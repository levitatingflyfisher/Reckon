# Reckon — Yellow Paper (formal spec)

## 0. Register

"Yellow paper" is a convention (borrowed from the Ethereum Yellow Paper) for a *rigorous
formal specification*. This document is **precise about intent and current behaviour**;
it is **not** a machine-checked proof and **not** a cryptographic security proof. The code
was authored by an AI assistant — treat this spec as the intended contract and **check the
code against it**, not the other way round. Where code and spec disagree, that is a bug in
one of them; the tests are the tie-breaker, then reality.

This paper specifies the two parts of Reckon with genuine formal content: the **ReckonParty
sync protocol** (§2–§5) and the **record-integrity invariants** (§6). The rest of the app
is described in prose in [concepts.md](../concepts.md) and the [reference docs](../reference/).

## 1. Notation

- `‖` is byte concatenation; `|x|` is byte length.
- `b64u(x)` is unpadded base64url; `b64(x)` is standard base64.
- `utf8`, `json` are the obvious encoders. `⊥` is "absent".
- A *blob* is an opaque byte string. The relay and the transport treat blobs as
  uninterpreted.

## 2. Objects

| Object | Definition |
|---|---|
| `K` | a 256-bit symmetric key (AES-GCM-256) |
| `Party` | a client-side decision object (question, options, method); serialised to JSON |
| `Ballot` | a client-side vote (approval set or ranking); serialised to JSON |
| `E(K, m)` | the authenticated-encryption envelope of §3 |
| `pid`, `bid` | client-chosen party id and ballot id (strings) |
| relay state `S[pid]` | `(party: blob ∪ {⊥}, closed: bool, ballots: bid → blob)` |

## 3. The encryption envelope

Encryption is **AES-GCM-256** (`party_crypto.dart`). For a JSON-serialisable object `d`:

```
E(K, d) = nonce ‖ ct ‖ tag
        where (ct, tag) = AES-GCM-256.Enc(K, nonce, utf8(json(d)))
              nonce  is a fresh random 96-bit value per call   (|nonce| = 12)
              tag    is the 128-bit GCM authentication tag       (|tag|   = 16)
```

Decryption `D(K, blob)` splits `blob` as `nonce(12) ‖ ct ‖ tag(16)`, runs GCM
verify-then-decrypt, and returns `json⁻¹(utf8⁻¹(ct))`. **`D` throws on any tag mismatch**
(wrong key, or a tampered blob). This is the integrity/authenticity guarantee: a blob that
verifies was produced by a holder of `K` and has not been altered.

**Key material.** `K` is generated by the AEAD's CSPRNG (`newSecretKey`), 32 bytes. Its
transport form is `keyString = b64u(K)` (padding stripped); `fromKeyString` re-pads to a
multiple of 4 before decoding.

**E1 (nonce freshness).** A fresh random nonce is drawn on every `E` call. GCM security
requires nonces never repeat under a fixed `K`; the spec forbids any code path that
encrypts with a caller-supplied or reused nonce.

## 4. The join link and key secrecy

A join link is:

```
URL = base ‖ "/join/" ‖ pid ‖ "#k=" ‖ keyString
```

`parse(URL)` (in `party_link.dart`) recovers `(relayBaseUrl = scheme://authority,
pid = segment after "join", keyString = fragment param "k" or a bare fragment)`, and
returns `⊥` if `pid` or the key is missing.

**K1 (key-secrecy invariant).** `keyString` appears **only** in the URL *fragment*. By the
URI/HTTP standard, conformant clients never transmit the fragment to the server. Therefore
`K` is never sent to the relay (or any server), and the relay cannot decrypt any blob.

**Corollary (access model).** Possession of the link *is* the capability: anyone with
`(base, pid, K)` can read and write the party. There is no additional per-voter
authentication (see §8).

## 5. The relay protocol

The relay (`relay/`, client in `party_relay.dart`) is a key/value store of blobs. Its
per-`pid` state `S[pid] = (party, closed, ballots)` evolves under exactly these
transitions:

| Operation | Precondition | Effect | Failure |
|---|---|---|---|
| `PUT /parties/{pid}` `⟵ blob` | — | `party := blob`; on first publish `closed := false`, `ballots := {}` | — |
| `GET /parties/{pid}` | `party ≠ ⊥` | return `(party, closed, ballots)` (blobs as b64) | `404` if `party = ⊥` |
| `PUT /parties/{pid}/ballots/{bid}` `⟵ blob` | `party ≠ ⊥` ∧ `¬closed` | `ballots[bid] := blob` | `404` unknown, `409` closed |
| `POST /parties/{pid}/close` | `party ≠ ⊥` | `closed := true` | `404` unknown |

**I1 (ballot idempotency).** `ballots[bid] := blob` is an overwrite keyed by the
client-chosen `bid`. Re-submitting the same `bid` replaces the prior blob — this is how a
voter changes their mind — and submitting a new `bid` adds a ballot. The relay performs no
merge and no tally.

**I2 (monotone close).** `closed` transitions `false → true` only; once closed, `submitBallot`
is rejected with `409`. There is no reopen transition.

**I3 (size bounds).** A stored blob is bounded (256 KB server-side). The client additionally
**streams `GET` responses under a hard 1 MB cap** and aborts if exceeded — the relay host is
named in an untrusted join link, so a hostile or oversized body (with a missing or lying
`Content-Length`) must never be buffered unbounded.

**Z (zero-knowledge property).** Define the relay's *view* as its persistent state plus all
its responses. By construction, the view is a function of only:

```
{ E(K, ·) blobs, client-chosen ids (pid, bid), the closed bit, blob sizes, timing }
```

and **contains no plaintext and no key** (K1). Hence an adversary in full possession of the
relay learns nothing about the question, the options, or any voter's choice beyond the
*count* and *sizes* of ballots and coarse timing. "Zero-knowledge by construction" is exactly
this statement — it is not a proof about the AEAD, which is assumed sound (§8).

## 6. Record-integrity invariants

These govern the personal Reckon loop and are the app's honesty guarantees
([ADR-0006](../adr/0006-honest-record-blinded-repolls.md)).

**R1 (blinded re-poll).** Let `polls(c)` be the polls of case `c` and `p*` the in-progress
re-poll. The re-poll elicitation UI's inputs are **independent of**
`{ p ∈ polls(c) : p.pollNumber < p*.pollNumber }`. Prior leans are not shown, defaulted from,
or otherwise leaked before the user answers. The full series becomes visible **only** at the
reveal.

**R2 (computed-on-query record).** The record metrics are pure functions of the set of
*closed* case records `Ω = { (case, polls, satisfaction) }`, recomputed on read and **never
persisted** as ground-truth. Given satisfaction scores `s_i ∈ {−2,…,+2}`:

```
ClarityScore(Ω).value      = 0                                   if Ω = ∅
                           = clamp₀¹⁰⁰( round( (mean(s) + 2)/4 · 100 ) )   otherwise
ClarityScore(Ω).caseCount  = |Ω|
```

The `caseCount` is always reported alongside `value` so a high score on a tiny sample cannot
masquerade as a track record.

**R3 (calibration definitions).** For `CalibrationReport(Ω)`:

- `sampleCount = |Ω|`.
- `CategoryStat`: for each category `g`, `meanSatisfaction = mean{ s_i : cat(i)=g }`; sorted
  by `meanSatisfaction` descending.
- `ConfidenceBucket`: group each record by the **confidence of its last poll**;
  `meanSatisfaction` per bucket. (Records with no polls are excluded.)
- `meanLeanDrift = mean_{i : |polls_i|≥2}( max(lean_i) − min(lean_i) )`, and `0` if no
  record has ≥2 polls.

All four are deterministic in `Ω`: change the inputs and the numbers move; there is no
stored value to inflate.

## 7. Fail-safe behaviour

The system fails toward *reject / restart clean*, never toward silent corruption:

- **Blob authenticity (§3):** any GCM tag mismatch throws; a tampered or wrong-key blob is
  never accepted as data.
- **Untrusted relay body (I3):** a response exceeding the cap is aborted, not buffered.
- **Model download completeness:** a downloaded model is valid **iff** the atomic
  `.part → final` rename completed; completeness is *never* inferred from a guessed size. An
  unsatisfiable resume range (HTTP 416) or an ignored range (HTTP 200 where 206 was expected)
  causes the partial to be discarded and the file re-fetched clean, rather than looping or
  corrupting (`model_download_service.dart`).
- **LLM failure:** every `LlmService` call returns a recoverable sentinel (empty stream /
  fallback text) rather than propagating an exception to the UI.

## 8. What this does *not* establish

- **Not a cryptographic proof.** §3/§5 assume the underlying AES-GCM-256 implementation
  (`package:cryptography`) is correct and that E1 holds. This paper proves nothing about the
  primitive; it specifies how Reckon *uses* it.
- **No per-voter authentication.** Access is capability-by-link (K1 corollary). A leaked
  join link (with its fragment) leaks read/write access to that party. There is no identity
  layer and no defence against a participant submitting multiple `bid`s.
- **Availability is out of scope.** The relay's resistance to denial-of-service, and the
  durability of its (default in-memory) store, are deployment concerns, not guarantees here.
- **Metadata leaks remain.** Per Z, the relay still observes ballot counts, blob sizes, and
  timing. Reckon does not pad or mix to hide these.
